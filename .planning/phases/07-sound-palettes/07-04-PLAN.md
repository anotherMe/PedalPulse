# Phase 7, Plan 04: On Auto the sound changes by itself every few minutes, together with the chords; a name keeps it

## Phase Goal

**As a** rider, **I want to** have the engine change its whole sound set every few minutes, or keep one I like, **so that** a long ride never sounds the same and I can name what I want more or less of.

The app sends `auto` for the Palette selector at launch, so this is what the rider hears by default. This plan makes Palette Auto real: a random palette from the start, a new one every few minutes landing on a progression change, no quick repeats, new files joining by themselves, and a named pick that locks until Auto is picked again.

<objective>
Implement palette Auto rotation (D-05 to D-08) as a stage of the per-bar harmony memo that Plan 01 built, generalise the background prefetch to palettes, keep the named-pick lock (PAL-03), and prove rotation, landing, locking, replay, new files, broken files and bounded state in the library check.

Purpose: PAL-02 and PAL-03.
Output: modified harmony.scd, loader.scd, main.scd, library_test.scd and check.sh. No library file and no Python change.

Rules and decisions (CONTEXT D-05 to D-08; planner decisions marked, yolo mode, listed for the rider in Plan 06):
- State lives in the run (`~ppHarm[\palAuto] = (current:, holdLeft:, history:)`), so a Start begins a new rotation (D-08). The draw counter `~ppPalAutoPicks` is global (survives Stop/Start, like Phase 6's `~ppAutoPicks`); draws seed the thread with ((~ppAutoSeed * 1000003) + (~ppPalAutoPicks * 7919) + 15485863) & 0x7FFFFFFF, a salt different from the progression draws, so palette draws never shift the replayable progression order.
- Boundaries, for bar b: `chapter` is progChanged (a cycle starts with a different progression than the last one; true on a run's first bar). `phraseLine` is cycleBar == 0 and (the cycle is at least 4 bars, or b % 8 == 0) (planner decision: classic's one-bar cycle would otherwise allow a change on any bar, which is not a phrase boundary, ROADMAP criterion 2).
- First pick ("engage": run start, Auto newly selected, or Auto after a named pick): at the first bar that is a chapter or a phraseLine while no palette scan is queued or running, draw from the candidates minus the palette playing (~ppPalPlaying). Until then keep the palette that is playing, and queue a palette scan at each such bar so new files are found. This is explicit exception 1 to D-06, limited to the opening pick of a rotation and made for D-08 (it is the "start" D-08 asks to be random): a run's first bar is always a chapter, so after a Start with the files loaded the opening pick is on a progression change anyway; it lands on a plain cycle start only on a cold start (files still loading) or when Auto is selected mid-run, where waiting for the next progression change would keep the playing palette for 1-3 minutes (Phase 6 progression Auto holds the playing progression 32-64 bars when it engages, which is what happens at the app's launch-time Auto). Every later change follows D-06/D-07 exactly. Planner decision for RESEARCH Open Question 2: Auto picked after a named lock does not adopt the locked palette (RESEARCH A6 suggested adopting); it draws a different one at the next round start, because D-08 makes Palette Auto random rather than classic-first.
- Rotation: holdLeft counts down by one per built bar (song bars, so Stop pauses it, D-05). A change is due when holdLeft <= 0 or the current palette is no longer a candidate. With the progression selection \auto it lands only on a chapter (D-06, exact: progression Auto always changes within its 32-64-bar stay when it has another candidate, so no bar-count fallback is needed). Explicit exception 2, narrow: when the progression selection is \auto but no progression other than the playing one can be picked (~ppAutoCandidates.() minus the cycle's stem is empty; evaluated only on cycle-start bars while a change is due), progression Auto can never change, so the change lands on a phraseLine as with a named progression (D-07), and the first time this happens in a run ~ppLog prints `PedalPulse: only one progression can play on Auto, so Auto palettes change at the end of its round` (the line does not begin with "PedalPulse: palette ", so it never counts as a palette change). With a named progression it lands on a chapter or a phraseLine (D-07). Pick: candidates minus the current and the last two of the history (asArray.keep(-2)); if empty, minus the current only; if still empty, keep the current with a new hold. Hold: rrand(lo, hi).round bars with [lo, hi] = ~ppPalHoldBars, default [80, 128] (RESEARCH Open Question 1, as recommended). The hold alone is 2.9-5.7 minutes at 90-110 BPM; the wait for the next progression change (about 25 bars on average, at most a 64-bar progression stay) brings the average palette to about 4.7-5.7 minutes at 90-110 BPM (D-05's 4-6), with single palettes anywhere from about 2.9 to 8.5 minutes; with a named progression about 3-6 minutes. These real numbers are stated in the harmony.scd comment and, for the rider, in the README and the UAT script (Plan 06), which asks for the rider's BPM. History capped at ~ppAutoHistoryCap (8).
- Candidates (~ppPalAutoCandidates): registered palettes whose stem passes ~ppStemValid and whose file exists under the current library root, sorted by name. classic stays in (D-08).
- Prefetch: ~ppAutoPrefetch.(cat) (nil means \progressions, so every Phase 6 caller keeps working) queues the category; one background Routine on SystemClock drains the queue, scanning each category with the existing name rule, ~ppLibEnsure, failed-file memory by modification time, at most ~ppAutoCaps[cat] files (progressions 256, palettes 32, RESEARCH A11); ~ppAutoPrefetching stays true until the queue is empty (Phase 6 tests wait on it); ~ppAutoBusy.(cat) is true while cat is queued or being scanned.
</objective>
