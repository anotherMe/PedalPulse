# Phase 2, Plan 03: Beat-synchronous tempo glide with mid-glide retarget

## Phase Goal

**As a** rider, **I want to** start, stop and retempo a full trance groove from the app, **so that** tempo changes never jolt my ride.

After this plan, every BPM the rider sets (slider, entry, nudges, unchanged Python side) glides over two bars instead of snapping, starting on a beat, and a new BPM mid-glide bends the glide toward the new target without restarting or jumping. This closes TEMPO-01 and TEMPO-02.

<objective>
Replace Phase 1's "apply at the next beat" one-shot with one long-lived ramp stepper Routine on `~clock` that steers the tempo toward a mutable target, and adapt plus extend the headless smoke test to prove the glide, the beat-boundary start, the retarget and the edge cases.

Purpose: TEMPO-01 (glide over ~1-2 bars, beat-synchronous, no jolt) and TEMPO-02 (mid-glide retarget from the current tempo, no restart, no jump).
Output: updated `supercollider/main.scd`, `supercollider/smoke_test.scd`, `scripts/smoke_test.sh`.

Working decisions this plan implements (RESEARCH "Gray Areas" defaults; no CONTEXT.md for Phase 2; all reversible, tuned by the end-of-phase listening check):
- Glide length 8 beats (2 bars), named `~ppRampBeats` so CTRL-02 (v2) can expose it later.
- Linear in BPM (constant BPM per beat for each glide). STATE.md flags the curve shape for a listening spike; the curve is isolated in the stepper's step computation.
- Step granularity 0.25 beat (16th note), named `~ppRampStepBeats`.
- Mid-glide retarget is immediate (next 16th tick), not re-quantized to a beat.

**Planner refinement of RESEARCH Pattern 1 (same idea, safer mechanics):** the stepper itself engages new targets; the `/pp/bpm` handler only stores the latest clamped value. RESEARCH's example engaged from-rest glides in a separate `schedAbs` callback. That would put two items on `~clock` at the same whole beat with no defined execution order. Its example also never reset the rate to 0 after landing, so every glide after the first would skip the beat-boundary start. With one writer of `~clock.tempo`, neither problem can occur.
</objective>
