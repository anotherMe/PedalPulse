# Phase 2, Plan 02: Start/Stop button in the app

## Phase Goal

**As a** rider, **I want to** start, stop and retempo a full trance groove from the app, **so that** tempo changes never jolt my ride.

After this plan the rider can stop and restart the music from the PedalPulse window with one button, on top of the `/pp/play` path Plan 01 proved. This closes GUI-02's app half.

<objective>
Add a `PlayController` to `python_app/bpm_logic.py` (test-first), then a single Start/Stop toggle button in `BpmWindow`, wire it to `OscClient.send_play` in `main.py`, and cover the button with real Tk 9 widget tests.

Purpose: GUI-02 requires the user to start and stop the music from the GUI.
Output: updated `python_app/bpm_logic.py`, `python_app/view.py`, `python_app/main.py`, `python_app/tests/test_view_tk.py`; new `python_app/tests/test_play_logic.py`.

Working decisions this plan implements (RESEARCH "Gray Areas" defaults, no CONTEXT.md for Phase 2):
- One toggle button whose label names the action a click will perform ("Stop" while playing, "Start" while stopped), not two buttons. Fits Phase 1's compact window (D-12). Reversible: view-only.
- No debounce: Start/Stop is a discrete click, not a drag.
- The app starts in the playing state and sends it once on launch, matching the engine's autostart (Phase 1 D-15) and the GUI-as-source-of-truth rule (D-23).

Scope note: STATE.md's open review finding WR-01 (Up/Down nudge BPM while the entry has focus) is NOT fixed here. STATE.md slates it for "before adding more GUI controls in Phase 3". This plan's button takes no focus and adds no key binding, so it neither depends on nor worsens WR-01.
</objective>
