# Phase 3, Plan 01: EPIC end to end in the engine (tracer)

## Phase Goal

**As a** rider, **I want to** pick my effort zone and set the volume, **so that** the music's energy matches my interval without clipping.

This plan proves the one new mechanic that crosses every layer: Python sends `/pp/epic`, sclang validates it, one smoothed EPIC value drives one FX synth (drive, filter, richness, reverb) between the groove and the limiter, and the rider hears the change. The first task wires that path end to end through the real Python client and proves the output gets brighter. The second task proves the glide (EPIC-02), the engine's input contract (clamp, malformed, loopback) and leak-free re-evaluation. Plan 02 puts the five zone buttons on this exact client; Plans 03 and 04 add master volume.

<objective>
Add the `/pp/epic <float 0-100>` control: `config.OSC_EPIC_ADDRESS`, `OscClient.send_epic` plus an `--epic` CLI option, and in `supercollider/main.scd` a raw EPIC control bus, one `Lag.kr` smoother synth, one smoothed EPIC bus and one persistent `\ppFx` synth in a new FX group between the instrument group and the master group. Extend the headless smoke test so each behaviour is checked through the real engine.

Purpose: EPIC-01 (EPIC 0-100 drives filter cutoff, drive/saturation, reverb amount and synth richness together) and EPIC-02 (EPIC changes glide, no steps or clicks). This is the tracer slice for Phase 3, the way Phase 2's `/pp/play` tracer proved its path first.
Output: updated `python_app/config.py`, `python_app/osc_client.py`, `python_app/tests/test_osc_client.py`, `supercollider/main.scd`, `supercollider/smoke_test.scd`, `scripts/smoke_test.sh`.

Working decisions this plan implements. No CONTEXT.md exists for Phase 3 (the user chose to continue without one); these are the 03-RESEARCH.md "Gray Areas" defaults adopted as working decisions, plus the still-binding Phase 1/2 decisions listed in RESEARCH "User Constraints":
- Wire contract `/pp/epic <float>` on sclang's language port, loopback-only, engine clamps to 0-100 (Phase 1 D-19 pre-named this address; rated costly, see Task 1).
- One raw bus, one `Lag.kr` smoother (lag 1.5 s, tunable through `~ppEpicLagSecs`), one smoothed bus, one `\ppFx` synth deriving all four parameters (RESEARCH Patterns 1 and 2). Chain order: drive, filter, richness, reverb. "Synth richness" is a high-frequency exciter blend (RESEARCH Assumption A1). All constants are reversible and get tuned by ear in Plan 02's listening check.
- Default EPIC is 10 (the Recovery zone) on a fresh boot; re-evaluation keeps the last value, like `~bpm`.
- The six instrument SynthDefs and the tempo stepper are not touched. EPIC never writes tempo (STATE, Phase 2 decision).

Planner corrections to RESEARCH (each verified during planning):
- `Synth`'s default addAction is `\addToHead` (verified in SCClassLibrary `Node.sc`). RESEARCH says to create the FX synth "normally" after the smoother, which would put it before the smoother. The FX synth is created with `\addToTail`.
- The lag time is a `lag` argument of the smoother SynthDef, set from `~ppEpicLagSecs` at instantiation. An environment variable read inside the SynthDef function would be frozen into the compiled def.
- Reverb is `FreeVerb2.ar` (stock stereo variant, verified on doc.sccode.org) on the two channels, not `FreeVerb.ar` multichannel-expanded into two mono reverbs.
- The send methods also catch `OverflowError`: a float beyond float32 range (for example `1e300`) raises a builtin OverflowError inside python-osc before any socket I/O (reproduced in the project venv during planning), so `python osc_client.py --epic 1e300` would otherwise crash.

Carry-overs folded in because this plan edits the same files: Phase 2 review WR-01 (send methods also catch python-osc's `BuildError`) and WR-02 (the bool-coercion test checks the exact type). Not addressed: Phase 2 IN-01 (glide timing), because Phase 3 must not touch the tempo mechanism.
